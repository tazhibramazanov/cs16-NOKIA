# Почему J2ME-версия CS 1.6 даёт ~6 FPS на Nokia E52

## 1. Железо и рамки задачи

Nokia E52: ARM11 (ARM1136) 600 МГц, **без GPU**, экран 240×320, 16 бит/пиксель
(EColor64K), Symbian S60 3rd Edition FP2. Кадр 240×320 — это 76 800 пикселей.
При 6 FPS игра обрабатывает ~460 тыс. пикселей в секунду. Для ARM11 600 МГц это
крайне мало: даже полностью программный рендер должен уверенно давать десятки
миллионов пикселей в секунду, если внутренний цикл — целочисленный и без
промахов кэша.

Ниже — разбор по источникам (файлы J2ME-проекта), затем — что именно меняется
в нативной версии.

## 2. Где именно теряется время

### 2.1. Формат кадра: ARGB32 + отдельный Z-буфер

`Render.java` хранит два `int[]`:

```java
public final int[] fb, zb;              // 240*320*4 = 307 200 байт каждый
```

Это 614 КБ на кадр только под буферы. Плюс `GameCanvas` держит `screen`,
`rotBuf`, `scaled` — ещё до 3×307 КБ. Итого более 1,2 МБ активно touched
памяти на кадр. У ARM1136 маленький L1D (32 КБ) и нет большого L2; каждый
проход (рендер → поворот → масштаб → `drawRGB`) вымывает кэш.

### 2.2. `Graphics.drawRGB` — ещё один полный проход по кадру

`GameCanvas.paint()` вызывает `g.drawRGB(buf, ..., false)`. MIDP-реализация
Symbian обязана сконвертировать ARGB `int[]` в формат экрана (RGB565) и
скопировать его в LCD-буфер. Это 76 800 конверсий на кадр, которые делает
**не наш код**, а слой MIDP, плюс синхронизация с UI-потоком через
`serviceRepaints()`. На E52 `serviceRepaints` ждёт UI-поток — это десятки
миллисекунд.

### 2.3. Поворот и масштабирование — отдельные полные копии

`GameCanvas.run()`:

```java
if (turned) { rotate(screen, fw, fh, rotBuf); f = rotBuf; ... }
int[] sc = fit(f, fw, fh);       // ещё один буфер и копия
...
g.drawRGB(...);
```

В горизонтальном режиме или на экране другого размера кадр проходит 3–4
полных копии. Каждая — 76 800 чтений + записей `int`.

### 2.4. Плавающая точка и деление в пиксельном цикле

`Render.drawSpan()` (и `drawSpanBL`, `drawSpanZ`) на каждые 16 пикселей делает
`1f / zi`, затем `s = (int)(sz * z * 65536f)`, `t = ...`, билинейный
`lightSample(...)` с четырьмя `float`-умножениями. На ARM11 без аппаратного
FPU (или с медленным VFP) это десятки тактов на операцию. Внутри пиксельного
цикла — только int, но пересчёт каждые 16 px всё равно дорог, а
`lightSample` вызывает ещё и 4 случайных чтения `light[]`.

`Render.setCamera()` каждый кадр вызывает `Math.cos/sin/tan` от градусов
(через `Math.toRadians`), `Render.setupGradients()` — `Math.sqrt` на каждую
грань, `drawMesh` — `Math.sqrt` на нормали/кватернионы.

### 2.5. Два случайных чтения памяти на пиксель

На каждый пиксель:

```java
F[p] = SH[((l >> 8) & 0x3F00) | (T[((t >> tsh) & tmask) | ((s >> 16) & smask)] & 255)];
Z[p] = zf;
```

`T[...]` — текстура (до 128×128 = 16 КБ, не в кэше при хождении по строкам),
`SH[...]` — таблица 64×256×4 = 64 КБ (тоже не в L1). Два промаха кэша на
пиксель — это ~20–40 тактов каждый на ARM11. При 76 800 px только это уже
несколько миллионов тактов на кадр.

### 2.6. Перерисовка неба и «непокрытых» пикселей

`fillUncovered()` проходит весь экран и для каждой дырки вызывает `addSky`,
а затем `drawSky()` рисует небо **по пикселям** с `1f/az` на каждый пиксель.
На открытых картах (dust2) небо занимает 20–40% экрана.

### 2.7. Аллокации и сборка мусора в игровом цикле

CLDC-рантайм на Symbian — это интерпретатор/KVM с простым GC. В кадре
постоянно создаются объекты:

* `Game.drawHud()`: `"" + p.deaths`, `Integer.toString`, конкатенации строк
  для таймера, счёта, киллфида;
* `Gfx.text()`/`Lang.t()`: `String` и `StringBuffer`;
* `Game.setLevel()`/`Render.setMap()`: массивы при смене качества;
* `Render.drawMesh()`: `new float[...]` при росте буферов;
* `GameCanvas.fit()`: `new int[]` при смене размера;
* MMAPI: объекты `Player`, `byte[]` под звук.

GC на E52 — это остановка мира. Даже 5–10 мс паузы на кадр при 15 мс бюджете
дают просадку в разы.

### 2.8. Звук через MMAPI

`MidpSys` держит очередь из 16 `Player`. Каждый выстрел — `setMediaTime(0)` +
`start()` (или создание нового `Player`). На Symbian это переход в нативный
MMF, выделение буферов и микширование силами ОС. Автоматический огонь
(10 выстрелов/с) превращается в постоянные дорогие вызовы.

### 2.9. Трассировка BSP и физика на `float`

`MapData.trace()` — рекурсивный обход BSP с `float`-умножениями и делениями.
На 10 игроков × несколько субшагов физики за кадр это заметно, но всё же
меньше, чем рендер. Основная проблема — `Math.sqrt` в `Move` и `Game` на
каждый шаг.

### 2.10. J2ME-оверhead

KVM выполняет байткод с проверками границ массивов, без агрессивной
инлайновой оптимизации. Один и тот же пиксельный цикл в C++ с `-O3` на
ARM11 быстрее в 5–15 раз ещё до всех архитектурных улучшений.

## 3. Что делает нативная версия

| Проблема J2ME | Решение в Symbian C++ |
|---|---|
| ARGB32 + `drawRGB` + поворот + масштаб | `CDirectScreenAccess`, прямая запись RGB565 в LCD-буфер, без промежуточных копий |
| `float`/`1f/z` в пиксельном цикле | целочисленный 16.16 внутри span/triangle; LUT `1/z`; `sin/cos` LUT |
| 2 случайных чтения на пиксель | таблица shade сразу в RGB565, текстуры 8-бит с mip-уровнями, индексы через сдвиги/маски |
| Перерисовка неба по пикселям | небо рисуется только в реально пустых span'ах; при `gfx=0` — плоский цвет |
| Аллокации в кадре | всё выделается на старте: пулы игроков, эффектов, звуков, моделей; в цикле — ни одного `new` |
| MMAPI на каждый звук | свой микшер 8 каналов, WAV предзагружены в RAM, вывод через `CMdaAudioOutputStream` в отдельном потоке |
| `Thread.sleep` + `serviceRepaints` | `CActive` + `RTimer::HighRes`, pacing по `User::NTickCount()` |
| Трассировка на `float` | та же геометрия, но без аллокаций; физика — 16.16 |
| Полный кадр 240×320 | динамическое разрешение (160×213 … 240×320) + bilinear upscale для «DLSS» |
| Nokia FR | кэш последнего 3D-кадра + сдвиг по Δyaw/Δpitch между реальными кадрами |

## 4. Бюджет кадра

Цель — 30 FPS при 240×320 (76 800 px):

* 76 800 px × ~8–12 тактов/px (индексированная текстура + shade + Z) =
  0,6–0,9 млн тактов;
* BSP-обход и клиппинг ~1000 граней × ~200 тактов = 0,2 млн;
* физика 10 игроков × 3 субшага × ~2 trace = ~0,3 млн;
* HUD/меню — 0,05–0,2 млн;
* **итого ~1,5–2 млн тактов на кадр**, при 600 МГц это 3–4 мс. Даже с
  двукратным запасом на промахи кэша — 8–12 мс, то есть 30–60 FPS.

J2ME при том же объёме работы тратит 160 мс на кадр. Разница — не в
алгоритме (BSP и span-буфер уже есть), а в среде исполнения и в формате
вывода.

## 5. Ограничения, которые нужно учитывать

* DSA нельзя использовать, когда поверх окна появляется системный диалог
  (сворачивание, звонок). Нужны `Abort()`/`Restart()` и пауза игры.
* Прямая запись в LCD-буфер требует, чтобы окно было полноэкранным и
  активным; иначе `CDirectScreenAccess::StartL()` не даст drawable.
* На E52 экран 16-битный; `EColor64K` — единственный быстрый режим. Проверять
  `ScreenDevice()->DisplayMode()` и не пытаться писать 32 бита.
* Нагрев: длительный рендер на 600 МГц без GPU греет корпус; ограничение
  20 FPS и динамическое разрешение — не только про батарею, но и про
  троттлинг.
* Память: карта dust2 ~1,3 МБ, текстуры моделей ~1,6 МБ, модели/анимации
  ~2 МБ, звуки ~1,5 МБ. Держать всё в RAM (≈8–10 МБ) выгоднее, чем читать
  файл в кадре; на E52 это допустимо.
